### How "SDL's controller test" was met

The design's testing plan names SDL3's controller test program (under "Checking what Windows sees"). M0 used `tools/padprobe.py` instead. It lists pads through SDL 2.32.10's joystick API (in pygame-ce), and PLAN.md 1.1 made it the tool for every pad check, so Claude can run those checks itself. It shows that the pads appear and what type each is. It doesn't check that the buttons map correctly. The design wants SDL3's test program for that, but no PLAN.md iteration runs it yet; the device and network matrix in 4.8 (Gate M3) is the closest fit. The user accepted padprobe as the M0 evidence at 1.4 (docs/decisions.md, "Gate M0 passes on padprobe, without a phone driving an Xbox pad").

## M0 scope

The design's M0 scope is "Python + vgamepad prototype; one Android phone drives an Xbox pad and a DualShock 4 pad; pick 3 target games".

| Scope item | Status |
| --- | --- |

| An Android phone drives an Xbox pad | **not done**; the gap is accepted, see below |
| Pick 3 target games | done: PICO PARK 2, Brawlhalla and Gang Beasts ([docs/target-games.md](../target-games.md)) |

**The Xbox pad gap.** PLAN.md 1.3 asked for one DualShock 4 pad, so `spike/server.py` never drove an Xbox pad from a phone. The gate only needs the pads to appear, and the user chose to pass M0 with the gap recorded (docs/decisions.md, "Gate M0 passes on padprobe, without a phone driving an Xbox pad"):
- The phone → UDP → server path doesn't depend on the pad type.
- In 1.1, stick moves sent from Python moved a virtual Xbox 360 pad (docs/decisions.md, "padprobe counts every Xbox pad, but watches them through XInput").
- No planned test before Gate M2 sends input to an Xbox pad. The shared mapping vectors in 2.1 cover DualShock 4 bytes only. The M1 host creates DualShock 4 pads only (2.9). The ViGEm tests in 2.5 and 3.2 check pad counts. So, as planned, a phone first drives an Xbox pad in the 3.8 playtest. See Carried forward.
